# Make re-reads cheap instead of forbidding them

GameSummoner should stop trying to talk Flash-Next out of re-reading after compaction. Instead it should make the re-read cheap, and stop throwing away the files the model was just working on. Every attempt so far to remove the need for a post-compaction read has failed: a fact block, a rule, file bodies pasted into the note, a model-written summary, and a fabricated `read_file` round carrying the real bytes. The fabricated round produced **the most reads of any arm, 19 against a baseline of 16**. The house evidence therefore reads the re-read as a verification habit, not as lost information. On our own data the first of the engineer's two ideas, "telling the model it did certain actions", works, and works strongly, but as a way to set precedent, not a way to deliver information. Seeded rounds are copied verbatim, failures included, and a seeded read **more than doubled reads per branch (2.77 to about 6.3)**. The second idea, JEV choosing files to read *for* the model, is contradicted in its broadest form (inject everything already read) and untested in the form that matters (inject only the one to three files it is about to read). It also has a hardware problem: JEV is a 27B model on its own card, and the brief says no extra GPUs. Three changes have the best evidence and fit the constraints. First, keep the recent working set through compaction. Today `drop_read_only_rounds` deletes even the newest read rounds, the exact opposite of what Claude Code, qwen-code and OpenHands do. Second, add a content-checked "already in context" read stub. Third, run a lab on the prompt line that tells the model it "will need to re-read". All three are harness-side, engine-neutral and safe for the KV prefix if they only act at compaction. The lab in `labs/context-management-research/README.md` orders these as arms. Its first arm is an oracle prefetch, which settles the JEV question before any money goes into a predictor.

## The re-read is a procedure, and the evidence keeps saying so

The waste is real and large. In the best game GameSummoner has produced, the Opus 5.5 frontier build d086d499669b, tier 1 was done by about step 75. **Steps 76 to 200 were 114 reads, 3 writes and 15 compactions, about $12 of roughly $22**. Each compaction was followed by re-reading the build's own large files until the 131K window filled again ([labs/frontier-ceiling/README.md](/home/nick/Documents/ai-agent-test/labs/frontier-ceiling/README.md)). The compaction-floor breakdown of the same build shows how tight the cycle is. Each compaction resumed at 42 to 84K tokens (mean about 62K), with 158 KB of game JS and a 54 KB spec on disk, and the window refilled in about ten turns ([labs/compaction-floor/README.md](/home/nick/Documents/ai-agent-test/labs/compaction-floor/README.md)). On prod Flash-Next, **reading is 52% of generated tokens, and 77% of reads are of files already read** ([labs/replay/README.md](/home/nick/Documents/ai-agent-test/labs/replay/README.md)).

The notes keep landing on "habit, not need". Six real compaction points were replayed at 18 samples per arm. **8 of 18 turns re-read with the file-state block, against 9 of 17 without it.** Four other arms were also null: a "must NOT be read again" rule, no code map, the map alone, and the bodies pasted into the note. The bodies delivered as a completed `read_file` round were worse than null ([docs/experiments.md:2093-2117](/home/nick/Documents/ai-agent-test/docs/experiments.md)). The lab framed it as "is the re-read about information, or about procedure?" ([labs/replay/arms_preread.py](/home/nick/Documents/ai-agent-test/labs/replay/arms_preread.py)), and the answer was procedure. The DeepSeek-Harness-style summary arm, which replaced history with an 8-section model-written summary, did no better. In one cell **72 of 94 turns re-read**, and the four turns right after the summary cut were all reads of files already shown (raw logs in `~/output/dsh-grid/`, never written up). When a replayed transcript was interrogated, the model called its own whole-design reading "cross-reference anxiety" and said "reading felt like progress" ([labs/spec-skeleton/README.md:708-714](/home/nick/Documents/ai-agent-test/labs/spec-skeleton/README.md)).

Two caveats keep this from being settled. First, every one of those null replay arms ran on the **local 27B, not Flash-Next**, and the replay README notes that prod's model "reads more and repeats more, and has not been probed". Second, the harness pushes the habit along. [prompts/build.txt:34-36](/home/nick/Documents/ai-agent-test/src/maestro/codegen/prompts/build.txt) still says "For context compaction, we will drop most of the history, and **you will need to re-read**". That line contradicts the compaction note's "Read a file only to edit it". The rule arm in the replay lab suggests wording has little pull, but nobody has removed the system-prompt line that predicts the re-read.

## The compactor deletes exactly what the model was looking at

The most actionable finding is mechanical. When `compact()` runs, it strips all reasoning and dedupes superseded writes. It then calls `drop_read_only_rounds`, which removes **every** round whose program only read, listed, checked syntax or played, however recent that round is ([src/maestro/codegen/build_steps.py](/home/nick/Documents/ai-agent-test/src/maestro/codegen/build_steps.py)). So the file the model read two turns ago, which is almost certainly part of its working set, leaves context at the moment the model resumes. The note that replaces it says "Every file is on disk exactly as you last wrote or read it". The file-state block says reading again "returns exactly what you were shown". Neither puts those bytes back in front of the model. The surviving floor (about 60K tokens, the newest written body of every file) holds what the model *wrote*, not what it most recently *looked at*.

Every production design in the notes does the opposite. Claude Code re-reads the **5 most recently read or edited files fresh from disk, at up to 5K tokens each and 50K total**. It skips files already visible in preserved messages and also re-attaches the plan and skills ([claude-code-best compact.ts](https://github.com/claude-code-best/claude-code/blob/HEAD/src/services/compact/compact.ts)). qwen-code, the open-weight reference aimed at Qwen models, ported the same 5 / 5K / 50K constants in September 2026 ([QwenLM postCompactAttachments.ts](https://github.com/QwenLM/qwen-code/blob/main/packages/core/src/services/postCompactAttachments.ts)). OpenHands keeps the newest half of events verbatim so "the agent has an easy time continuing the current task" ([OpenHands condenser README](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/context/condenser/README.md)). SWE-agent keeps the last N observations and masks older ones ([history_processors.py](https://github.com/SWE-agent/SWE-agent/blob/main/sweagent/agent/history_processors.py)).

This matters for the engineer's idea. **Claude Code's restore step already is a prefetch, with recency as the predictor.** It is a deterministic one that needs no GPU. Any learned predictor has to beat it.

Claude Code also teaches a correctness lesson. Its unchanged-read stub ("File unchanged since last read ... refer to that instead of re-reading") logged **1,734 dedup hits in 2 hours with no Read error regression**. But Claude Code clears that cache at compaction, because a stub pointing at bytes that are no longer in context would be a lie ([FileReadTool.ts](https://github.com/claude-code-best/claude-code/blob/HEAD/packages/builtin-tools/src/tools/FileReadTool/FileReadTool.ts)). It also had a stale-stub bug when files changed outside its own tools ([issue #60684](https://claudeissues.com/issue/60684-bug-read-tool-returns-file-unchanged-after-external-on-disk-edits-serving-a-stal)). GameSummoner's file-state block makes the same "unchanged" claim *after* the bytes are gone. That explains why it does nothing.

The stub to build is one that fires only when the file's current bytes really are still in the live transcript, checked by content hash rather than by tracking our own writes. A stub like that cannot stop a procedural re-read. It can turn a 13 to 20K-character re-read into a one-line answer, which keeps a verification habit from refilling the window. A third-party dedupe server measured **-2.6% savings on top of Claude Code's native stub** ([Glama listing](https://glama.ai/mcp/servers/ea9d6jki41)). Read the other way, the native stub already captures most of what is available, and GameSummoner does not have it.

## Synthetic history steers behaviour hard, in whatever direction it points

"Tell the model it did X" works. The outside evidence comes mostly from attacks. Every model given fabricated harness history of up to 78 turns accepted it, across Claude Code, Codex, Kiro-CLI and Pi ([Darktrace](https://www.darktrace.com/blog/hijacking-agentic-harnesses-to-attack-an-organization)). Many-shot faux dialogues follow scaling laws in the number of shots ([Anthropic](https://www.anthropic.com/research/many-shot-jailbreaking)). Trajectory exemplars lift ALFWorld from 73% to 89% ([arXiv 2505.00234](https://arxiv.org/abs/2505.00234)). Self-hosted SGLang and llama.cpp impose no prefill restriction.

The labs/seeded-corrections work on Flash-Next IQ3_S shows the same force inside our harness, both helping and hurting. It seeded one successful `print(read_file("design/design.md", lines=100))` round with its real harness reply. **Lost turns at fix starts halved, from 0.84 to 0.42 per branch, and direct native calls went from 37 branches to 0**. The same seed raised reads ([labs/seeded-corrections/README.md](/home/nick/Documents/ai-agent-test/labs/seeded-corrections/README.md)).

The failures are the instructive part:

- **Failures are copied.** A seeded `open()` came back verbatim on the first real turn. After compaction, the 3-round seed **doubled direct calls, 18 to 36 branches (p=0.012)**.
- **A bare listing invites `open()`.** A seeded file listing with no read beside it pushed refusals from 95 to 174 branches, because the model then tried to `open()` the listed paths.
- **The successful read seed planted a dead `import subprocess` habit.** It took a nudge to clear it.

Across arms, **reads per 5-turn branch rose from 2.77 to roughly 6.2-6.5** (relay from the seeded-corrections session, [peer notes](/home/nick/Documents/ai-agent-test/labs/context-management-research/research_notes/Low%20impact%20context%20compaction/peer_seeded_rounds.md)).

So synthetic history is a strong precedent channel and a poor information channel. Flash-Next treats a harness-written turn as "what I do here" and repeats its shape. A seeded read teaches "I read", not "I know". That fits the 19-versus-16 replay result. It also suggests the useful way to apply the lever to read minimization. Do not seed the content the model will want. Seed the cheap *way* of getting it. Two candidates are a single ranged read sized off the code map's line ranges (`offset`/`lines`), or a hit on the in-context stub. The precedent the model copies is then the low-byte one. The metric has to be **bytes brought in per build, not read count**, because the count may well go up. Any seed must follow the house pattern that worked: native tool-call format, real bytes from a real code path, well-formed ids, pinned through compaction. It must never contain a failure.

## JEV prefetch: contradicted broadly, untested narrowly, and short a card

The engineer's idea is to have JEV read the compacted context, predict which files the model will read next, and read them for it. It holds up on interface and latency. JEV takes state, question and options and returns calibrated probabilities. It scores item lists yes/no against a `keep_over` threshold and runs at **about 68 ms per read on a warm box**, so ranking a 20-file game costs 1 to 2 seconds (memory `project_jev_decide_box.md`; `gamesummoner-images/contract/decide.py`).

The literature backs the *prediction* half. File-level localisation reaches **63 to 93% top-1** on SWE-bench Lite ([LocAgent](https://arxiv.org/abs/2503.09089); [BLAgent](https://arxiv.org/pdf/2605.17965)). General next-tool prediction is weaker: 27.8% top-1 and 43.9% top-3 in PASTE ([arXiv 2603.18897](https://arxiv.org/html/2603.18897v1)). Small, self-written game repos with a code map and import edges should be easier to predict than Python bug localisation. That is a reasonable prior, but it has not been measured.

The *injection* half is where the evidence turns against the idea. Every speculative-action system with measured gains, including Speculative Actions at about 20% latency saved ([arXiv 2510.04371](https://arxiv.org/abs/2510.04371)) and PASTE at up to 48.5%, speculates **into a cache** and commits only when the agent issues the matching call. That saves tool latency. A GameSummoner `read_file` takes microseconds, so it saves almost nothing here. The cost GameSummoner pays is the turn and the tokens, which means injecting into context. **No study measures that variant.** The closest result is a cost study: whole files against pruned context, single-shot, cost three times the tokens and resolved nominally fewer tasks (27.1% against 35.7%, not significant) ([arXiv 2607.09691](https://arxiv.org/html/2607.09691v1)). Our own 19-versus-16 arm is the broad version of the idea, and it lost.

What it did not test is a *narrow, correct* injection of only what the model reads next. That was a 60K-character dump of everything already read, on the 27B. So the honest verdict is "contradicted for inject-all, untested for inject-top-k". The cheapest way to settle it is an **oracle**. Take the files that existing control branches actually read in the five turns after a real compaction point, inject exactly those, and see whether the model still reads them. If perfect prediction does not cut reads, no predictor can, and JEV's accuracy stops mattering. If it does cut reads, the next question is whether JEV beats the free recency predictor Claude Code ships.

Two practical problems stand regardless of the outcome. First, JEV is Qwen3.8-27B with a readout head. In prod its decide box is cold-booted once per game, taking about 120 s, and runs with `--max-running-requests 1`. Running it through a build means a warm card for the length of the build, which breaks the no-extra-GPUs constraint, unless the planned JEV head on Flash-Next hidden states lands ([labs/jev-on-flash-next/README.md](/home/nick/Documents/ai-agent-test/labs/jev-on-flash-next/README.md)). Second, calibration does not transfer automatically. The 0.8B qev candidate failed as a replacement on design decisions ([labs/qev-decide/README.md](/home/nick/Documents/ai-agent-test/labs/qev-decide/README.md)), and JEV's latency on a 40 to 60K-token compacted state has not been measured. The predictability question can be answered offline and for free: `turns.jsonl` and `reads.json` already label every post-compaction read.

## What to keep, what to skip, and what the prefix costs

The external evidence that holds up best is observation masking. Old tool outputs become placeholders while the model's actions stay. In SWE-agent on SWE-bench Verified it **halved cost and matched or beat LLM summarisation** (Qwen3-Coder 480B: 53.4% raw, 54.8% masked, 53.8% summarised). Summaries made runs **about 15% longer** ([Complexity Trap, arXiv 2508.21433](https://arxiv.org/html/2508.21433v3)). Anthropic reports 84% fewer tokens from tool-result clearing on a 100-turn task ([Claude blog](https://claude.com/blog/context-management)).

GameSummoner's compactor is already a masking compactor: it stubs write bodies and drops read rounds. That favours tuning what it keeps over switching to summaries. Summaries also fail the artifact-trail test. Factory's probe eval scored "which files changed and how" lowest for every method, **2.19 to 2.45 out of 5** ([Factory](https://factory.com/news/evaluating-compression)).

The **thinking caveat** cuts against aggressive trimming. In the same paper, thinking-enabled Gemini 2.5 Flash fell from 40.4% to 36.4% under masking and to 31.4% under summaries. Thinking-enabled Qwen3-32B held up (23.0% raw, 24.6% masked). Flash-Next runs with thinking on, which was measured as a real quality gain, and `strip_reasoning` discards all of that reasoning at every compaction. A smaller keep target or harder masking therefore has to be judged on game quality, not just tokens. Carrying the last round's reasoning through the cut is a cheap thing to test alongside keeping the working set.

**KV-prefix cost** sets *when* any of this may act. On our engines, any edit behind the cache frontier means a full re-prefill: about 15 s at 83K, and about 27 minutes across one spec-skeleton build ([labs/spec-skeleton/README.md](/home/nick/Documents/ai-agent-test/labs/spec-skeleton/README.md)). Keeping reasoning in the transcript is what made 49,361 of 49,378 tokens reusable ([docs/experiments.md:2186-2190](/home/nick/Documents/ai-agent-test/docs/experiments.md)). Rolling per-turn masking, of the kind SWE-agent mitigates with a `polling` slack, would pay that cost every turn. The rules that follow are:

- History edits happen only at compaction, which already pays one full re-prefill.
- Restored files and any prefetch are appended to the note at that same boundary.
- The in-context stub is an appended tool reply, so its prefix cost is zero.

The trade-off to watch is that keeping a 25 to 30K working set raises the floor. That is the qwen-code budget scaled to our window, an extrapolation and not a measurement. A higher floor means compaction comes sooner. The stub is the change that keeps the larger floor from refilling the window.

| Lever | Evidence | Fits constraints | Risk | Verdict |
|---|---|---|---|---|
| Keep newest read rounds / restore recent files | Claude Code, qwen-code, OpenHands ship it; unmeasured for re-reads | Harness-only, compaction-time | Higher floor, sooner compaction | Lab arm, high priority |
| In-context, content-hashed read stub | Claude Code soak 1,734 hits/2h, no regression | Harness-only, append-only | Model routes around it (`open()`, slices) | Lab arm, high priority |
| Remove build.txt:34 "you will need to re-read" | None; a rule arm was null on 27B | Prompt change | Small effect | Lab arm, cheap |
| Seeded ranged-read precedent | Seeds imitated verbatim (Flash-Next) | Harness-only | Imitated failures, more reads | Lab arm, measure bytes |
| Oracle prefetch into context | Inject-all lost 19 vs 16 (27B) | Compaction-time | Bloat, more reads | Lab arm 1, decisive |
| JEV predictor | Interface fits; no code-nav result | Needs a warm 27B card | Fails "no extra GPUs" | Only if oracle and offline scoring pass |
| LLM summary compaction | DSH arm still 72/94 re-reads; +15% turns | Extra model call | Thinking models hurt | Skip |
| KV eviction / learned memory (KVzip, REMORY) | Not in SGLang; needs engine work or fine-tune | Engine fork | Exact-recall loss | Skip |

## Conclusion

The question changes once the re-read is accepted as a habit. Stop asking how to give the model enough that it won't look again, and start asking how to make looking again nearly free and how to stop the harness from causing the forgetting. The compactor currently deletes the model's freshest reads, tells it nothing changed, and its system prompt predicts that it will re-read. Each of those can be fixed without a GPU, an engine fork or a summary model. Synthetic history is the most powerful tool in the set, and it should be aimed at the *shape* of reads rather than their content, because Flash-Next copies precedent exactly.

The JEV idea earns one decisive, cheap test before any further investment. The oracle arm costs a few hundred replay branches, and offline scoring against turn logs costs no build at all. Only if both pass does it make sense to spend a card, or the JEV-on-Flash-Next work, on a predictor that has to beat "the five files it touched last". A residual remains that no compactor fixes. Much of the Opus waste came after tier 1 was green, when the build had nothing left to write and verification was all it could do. That is a done-condition problem as much as a compaction one.
