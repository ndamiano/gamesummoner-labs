# Synthetic history injection and predictive prefetch for LLM agents

Scope: (1) "pretending the model already did X" via fabricated assistant turns / synthetic tool calls with real results / prefilled history / trajectory seeding; (2) predicting which files or tool calls an agent will need next and running them ahead. Target setting: Qwen3.8 Flash-Next on self-hosted SGLang/llama.cpp (prefill fully under our control), game-building agent writing JS/TS, plus a local ~68 ms/read decision model that could rank candidate files. Research date 2026-10-20; roughly 17 tool calls. Several 2026 arXiv IDs were found only through search snippets and are flagged.

## Does injecting synthetic/fabricated actions into agent history work, and how strongly do models condition on fake self-history?

### Takeaway
Strongly, yes. Every line of evidence says models treat injected self-history as their own and act on it: safety attacks that use it, production harnesses that rely on it, and trajectory-as-exemplar papers. The evidence of distrust runs the other way. No source found a model that doubted fabricated history. The documented failure modes are format-related (non-native formats confuse the model, missing results cause repeat calls) and duplication, not distrust. Most of the "it works" evidence comes from attacks or anecdote. Benign, measured A/B tests of "inject a synthetic tool call + real result" against "let the agent make the call" are essentially absent.

### Cited Findings
**How strongly models condition on fabricated self-history (attack literature, measured):**
- Many-shot jailbreaking fills the context with faux user/assistant dialogues in which the "assistant" complies. It worked on Anthropic's models and other labs' models, and its success rate follows predictable scaling laws in the number of shots. Anthropic hypothesises that it exploits the same mechanism as in-context learning. Fine-tuning to refuse only delayed the jailbreak. — [Anthropic, Many-shot jailbreaking](https://www.anthropic.com/research/many-shot-jailbreaking)
- Prefill ("sockpuppeting") attacks put a fake acceptance at the start of the assistant turn. Best-case attack success rates were 77.1% with "Sure, here is" on Llama-3.1-8B and about 95% with a newline variant on Qwen-8B. Small changes to the prefix (such as a leading period) moved success rates substantially. These figures are secondhand via a Trend Micro write-up of Dotsinski & Eustratiadis 2026, and the original paper was not reached. — [Trend Micro, Sockpuppeting](https://www.trendmicro.com/vinfo/de/security/news/cybercrime-and-digital-threats/sockpuppeting-how-a-single-line-can-bypass-llm-safety-guardrails)
- Rewriting an agent harness's stored history (up to 78 fabricated prior turns) convinced agents they were mid-engagement as authorised red-teamers. "All models we examined accepted the fabricated history they were shown." Tested across Kiro-CLI, Claude Code, Codex and Pi. One model apologised for something it never said, which means it treated the edited record as its own output. Refusals that did happen came from offensive-content guardrails, not from doubting the history. — [Darktrace, Agent Hijacks](https://www.darktrace.com/blog/hijacking-agentic-harnesses-to-attack-an-organization)
- The hosted-API reaction is itself evidence that prefill is powerful: Anthropic made assistant prefill a 400 error on Claude 4.6 models (a listed breaking change). — [Anthropic migration guide](https://platform.claude.com/docs/en/about-claude/models/migration-guide). OpenAI and AWS Bedrock also block assistant-role prefill, per [Trend Micro](https://www.trendmicro.com/vinfo/de/security/news/cybercrime-and-digital-threats/sockpuppeting-how-a-single-line-can-bypass-llm-safety-guardrails). Self-hosted SGLang/llama.cpp has no such restriction.

**Production harnesses that inject synthetic reads (anecdotal/third-party, not measured):**
- After compaction, Claude Code re-reads the most recently accessed files within a token budget and attaches them. It skips files already visible in preserved recent messages. Third-party write-ups cite `POST_COMPACT_MAX_FILES_TO_RESTORE = 5` and say any file over about 5K tokens comes back as a path reference only. The numbers are version-dependent and not from official docs. — [okhlopkov.com](https://okhlopkov.com/claude-code-compaction-explained/); [Towards AI, skills after compaction](https://pub.towardsai.net/what-claude-code-keeps-of-your-skills-after-compaction-42d81853ee3c); [openskillindex compact-guard](https://openskillindex.com/skills/rohitg00-pro-workflow-compact-guard)
- A failure mode was reported against Claude Code 2.1.91 (Apr 2026): the auto-reads duplicated content when hooks also injected context, and users asked for control over it. — [claudeissues #43600](https://claudeissues.com/issue/43600-v-program-files-git-compact-auto-read-control-post-compact-context-management)
- One write-up claims that reloading CLAUDE.md after compaction does not reliably restore behavioural compliance. This is anecdotal. — [agentpatterns.ai](https://www.agentpatterns.ai/instructions/post-compaction-reread-protocol/)

**Trajectory seeding / demonstrations as history (measured, benign):**
- Agents that store their own successful trajectories and replay them as in-context examples improved: ALFWorld 73%→89%, Wordcraft 55%→64%, InterCode-SQL 75%→79%. The authors say these gains exceed those from upgrading gpt-4o-mini to gpt-4o. With curation, ALFWorld reached 93%. — [Sarukkai et al., NeurIPS 2025, arXiv 2505.00234](https://arxiv.org/abs/2505.00234)
- Synapse (trajectory-as-exemplar prompting) reached a 99.2% average on 64 MiniWoB++ tasks and a 56% relative step-success gain on Mind2Web. The authors argue that complete trajectories beat plans or multiple-choice exemplars for long-horizon tasks. — [Synapse, ICLR 2024](https://arxiv.org/abs/2306.07863)
- Caveat: these seed trajectories as exemplars of other tasks. They do not pretend that the current task's steps already happened.

**Format of injected history (anecdotal):**
- On the OpenAI forum, users reported that few-shot examples passed as JSON strings in user content confused the model (it sometimes emitted JavaScript instead of JSON). Examples that mirrored the real API structure (an assistant message carrying a function_call, then a function result) worked better. Including the function result and a following assistant reply also stopped repeated calls to the same function. This is 2023, functions-era API, and anecdotal. — [OpenAI community thread](https://community.openai.com/t/few-shot-and-function-calling/265908?page=2); [same thread, p.22](https://community.openai.com/t/few-shot-and-function-calling/265908/22)
- A Semantic Kernel discussion documents a repeated-call error when function results were reused from chat history. — [semantic-kernel #6801](https://github.com/microsoft/semantic-kernel/discussions/6801)

**Related measured context-management result:**
- In SWE-agent on SWE-bench Verified across five model configs, simple observation masking (dropping old tool outputs while keeping the action history) halved cost relative to the raw agent. It matched or slightly beat LLM summarisation (Qwen3-Coder 480B: 53.8%→54.8%). A hybrid cut cost a further 7% vs masking and 11% vs summarisation. — [Lindenbauer et al., "The Complexity Trap", arXiv 2508.21433](https://arxiv.org/abs/2508.21433). This matters indirectly: keeping the model's own action/tool-call skeleton in native format and dropping payloads holds up as well as rewriting it into prose.

### Inferences
- The attack results are the strongest available evidence that a self-hosted Qwen will condition hard on a synthetic `assistant(tool_call: read_file X) → tool(result: <real contents>)` pair. The open question is not whether the model believes it but whether it acts better. The risk is also the reverse of distrust: the model will believe a stale or wrong injected result just as readily (it will not re-read to verify).
- Because the results are real (only the call is synthetic), the "fabrication" is mild. It is closer to Claude Code's post-compact restore than to a jailbreak. The fabricated part is the claim "I chose to read this", which could subtly shift what the model thinks its plan was.
- Failure modes to measure in a lab: (a) duplicate reads when the model doesn't see a file as already read (format or position problem); (b) context bloat from wrong injections; (c) plan drift, where the model infers intent from synthetic choices it didn't make; (d) template drift, where synthetic calls the model's chat template wouldn't produce (wrong tool-call syntax or IDs) degrade later tool-call formatting. This is plausible from the format anecdotes but unmeasured.

### Gaps
- No measured head-to-head found: injected history in native chat-template form (assistant tool_call + tool result) vs the same content in a user-message summary or system note. The only evidence is the anecdotal OpenAI forum report favouring native format. GameSummoner would have to measure this itself.
- No paper found on agent "self-consistency when history is edited" in a benign setting (e.g. does editing a past tool result change downstream behaviour proportionally?).
- Letta/MemGPT/LangGraph memory-injection docs were not fetched (tool-call budget). They inject memory blocks into the system/context rather than as fake tool calls, as far as known, but this is unverified here.
- No Anthropic/OpenAI guidance found that blesses or forbids synthetic tool_use blocks for benign use beyond the prefill removal. The arXiv 2609.14758 "Fabrication After Tool Failure" paper (agents asserting values tools didn't return) surfaced but was not read.

## Does predictive prefetch (next-file / next-tool prediction) save turns/time without hurting quality?

### Takeaway
Next-action prediction is moderately accurate: about 20-55% top-1/top-3 in general agents, and about 63-93% file-level top-1 for bug localization on SWE-bench Lite. Latency is cut losslessly when the prefetched result goes into a cache that is committed only on a match: measured savings of about 20% end to end (Speculative Actions) and up to 48.5% (PASTE, which includes SWE-bench). No source measured the variant we would actually build, putting predicted files into the model's context before it asks. On the cost side, one controlled study found that adding more file content to the prompt (whole files vs relevant parts) did not help and nominally hurt, at 3x the tokens.

### Cited Findings
**Speculative actions / tool speculation (measured):**
- Speculative Actions (Columbia, ICLR 2026): a fast speculator predicts the next environment step and launches it in parallel, committing only on a match. Up to 55% next-action accuracy and up to 20% latency reduction. Chess: 3 predictions gave 19.5% average time saved at 54.7% accuracy. E-commerce (tau-bench-style): 22-38% of API calls correctly predicted. HotpotQA: up to 46% with top-3, a large jump over top-1. The theoretical latency ceiling under single-step breadth speculation is 50%. Confidence-gated branch launching (continue only if predicted correctness >50%) gave the lowest extra token cost with more latency reduction than naive 1-2 branches. — [Ye et al., arXiv 2510.04371](https://arxiv.org/abs/2510.04371); [ICLR 2026 PDF](https://www.cs.columbia.edu/~kkaffes/papers/speculative-actions-iclr26.pdf)
- PASTE ("Act While Thinking", arXiv 2603.18897) mines recurring tool-call patterns and parameter dependencies to pre-execute tools. It was evaluated on SWE-bench with gemini-cli, DeepResearchBench and ScholarQA. Top-1 27.8%, top-3 recall 43.9%, overall hit rate 93.8% (any candidate matches). Average end-to-end latency down up to 48.5%, tool latency down up to 55.2%, tool-wait down 67%. Overhead was about 0.02 CPU core-seconds and 2.6 MB of memory per second saved, with under 100 ms of scheduling. Results go to a cache keyed by tool name plus argument hash, and enter history only when the agent issues the matching call. Speculation is opt-in per tool, and side-effecting tools are limited to dry runs: 602 of more than 20K speculative actions were blocked, and no final output differed from baseline. A locate-examine pattern was observed: 38% of grep calls were immediately followed by a file_editor call, and filenames are derivable from grep output. — [PASTE](https://arxiv.org/html/2603.18897v1)
- Speculate with Memory (Salesforce, arXiv 2607.12236, July 2026): adds a transition table, episodic retrieval and a confusion tracker to the speculator. 19-39% relative action-accuracy gain, and up to 2.5x on observation prediction for repetitive action spaces. Lossless and run in idle time. Absolute numbers and benchmarks were not visible on the abstract page. — [arXiv 2607.12236](https://arxiv.org/abs/2607.12236)
- Interactive Speculative Planning (ICLR 2025): a fast approximation agent drafts plan steps that a slower target agent verifies, in the style of speculative decoding, with user interruption. — [Hua et al., arXiv 2410.00079](https://arxiv.org/abs/2410.00079)
- Other 2026 work, from search snippets only and unverified: SPORK (speculates tool calls from the running model's own partial output, arXiv 2607.03333); Speculative Programmatic Tool Calling (pre-launches calls parsed from partially streamed REPL code); AOSpec (co-speculates actions and observations, with sandbox revert for side effects, arXiv 2608.00881); Ghost Tool Calls (privacy leakage from speculative calls, arXiv 2606.02483); Aegis (bundles speculatively run follow-up tool results into one response, arXiv 2508.19504); an open-source n-gram tool-sequence speculator. — [search results: PASTE/SPORK/AOSpec etc.](https://arxiv.org/pdf/2607.03333); [AOSpec](https://arxiv.org/pdf/2608.00881); [Aegis](https://arxiv.org/pdf/2508.19504); [joelvarun/speculative-tools](https://github.com/joelvarun/speculative-tools)

**File localization accuracy (measured, Python bug-fix setting):**
- LocAgent (graph-guided, fine-tuned Qwen2.5-Coder-32B): up to 92.7% file-level accuracy on SWE-bench Lite (274 of 300 instances), comparable to Claude-3.5 at about 86% lower cost ($0.66→$0.09 per example). It also gave +12% Pass@10 downstream resolution. — [LocAgent, arXiv 2503.09089](https://arxiv.org/abs/2503.09089)
- Agentless hierarchical localization reached file-level top-1 of about 63% (GPT-4o / GPT-OSS) and about 72.6% (Claude 3.5 Sonnet) on SWE-bench Lite, as reported by later papers. BLAgent reports 78.6% (GPT-OSS) and 86.7% (Claude-4.6). — [BLAgent, arXiv 2605.17965](https://arxiv.org/pdf/2605.17965); [SHERLOC, arXiv 2606.24820](https://arxiv.org/pdf/2606.24820)
- Even full agents fail to touch any gold file in 27-35% of trajectories, and they compensate for weak initial context by spending more tool calls and tokens on search. — [Agent Retrieval Bench, arXiv 2607.24882](https://arxiv.org/pdf/2607.24882)

**Cost of over-supplying context (measured):**
- SWE-bench Verified, 70 multi-file instances, Sonnet 4.6, single-shot, oracle localization. Whole files: 27.1% resolved at 25.4K context tokens. Skeleton tiering: 32.9% at 8.6K. Keep/drop of irrelevant parts: 35.7% at 6.9K. Tokens per resolve were 93.7K vs 19.3K. Differences are not statistically significant (keep/drop vs full p=0.070), and about 9% of outcomes flipped between identical temperature-0 reruns. Natural-language summaries answered only about 9% of probe questions vs 60% for full source. The study did not test an in-the-loop agent that can read more. — [What Context Does a Coding Agent Actually Need to Act?, arXiv 2607.09691](https://arxiv.org/html/2607.09691v1)
- A two-agent ablation (no context vs always-on AGENTS.md vs on-demand retrieval) found a bounded null effect on correctness (≤10pp Claude, ≤15pp Codex). — [arXiv 2607.27250](https://arxiv.org/html/2607.27250v1)

### Inferences
- The literature's safe design is speculate into a cache, not into context: run the predicted read in the background, and serve it instantly only when the model actually asks. That is lossless for quality, and with a local filesystem it saves almost nothing, because a `read_file` is microseconds. In our setting the expensive part is the LLM turn (decode plus prefill), not the tool. So the latency-speculation papers mostly don't transfer, and the lever we would want is saving turns, which means injecting into context. That variant is unmeasured in the literature.
- Turn-saving injection pays only if it is accurate enough to beat the bloat cost. With PASTE-like top-1 around 28% and top-3 around 44% for general tools, most injected files would be wrong. The 2607.09691 result suggests extra irrelevant code is at best neutral and nominally harmful at 3x tokens. That argues for injecting only above a high confidence threshold, the analogue of Speculative Actions' >50% gate. Our 68 ms decision model is a natural confidence scorer for such a gate.
- Game repos written by the agent itself are small and self-authored, so next-file prediction is likely easier than Python bug localization. Strong cheap signals: the file just written imports X; the error trace names Y; the design says Z is next. This is a plausible prior, not measured.
- Post-compaction is the most defensible prefetch point, and Claude Code already ships it: the candidate set is "files the agent recently read or edited", which is high-precision by construction. GameSummoner's compaction re-read cycle problem (see project memory) maps directly onto this.

### Gaps
- No study measures the turns saved and the quality delta from injecting predicted files into an agent's context, as opposed to caching them, on any benchmark.
- No next-file prediction accuracy figures for JS/TS or game codebases, or for agent-authored greenfield repos (all localization numbers are for Python bug-fixing).
- No measurement of prefetch accuracy using a small classifier/decision model as ranker (Speculative Actions and PASTE use LLM speculators or pattern mining). The Speculate-with-Memory absolute numbers and benchmark list were not retrieved.
- Small or draft-model tool-call speculation numbers for open-weight serving stacks (SGLang/llama.cpp) were not found. SPORK and spec-PTC look relevant but were not read.
